# 교통민원 들리오 DLLIO

들리오는 시민이 일상적인 말로 쓴 교통민원을 읽고, 그 민원을 살피는 데 필요한 교통 자료 조회를 계획해 실행한다.
담당자는 민원 원문, 행정 검토용 요약, 조회 결과와 답을 한 화면에서 본다.

민원 게시판은 운행 기록을 찾기 위해 시민에게 노선·정류장·구간·시간을 양식에 맞춰 적도록 요구한다.
들리오는 시민이 쓴 글에서 그 대상과 맥락을 읽고, 교통 자료로 볼 수 있는 조회로 옮긴다.

## 처리 흐름

```text
원문 → 문제 유형(L2) 판정 → 문제별 이동 추출 → 후보 준비·조회 선택·계획(L1) → 조회 실행 → 답과 화면 구성 → 뷰어
```

- **문제 유형**: 판정 모델이 원문 전체를 읽고 [L2 catalog](docs/L2_CATALOG.md)의 유형마다 이 민원에 그 문제가 있는지 판정한다.
- **이동 추출**: 언어 모델이 고른 유형마다 출발지·도착지, 시간대, 시민이 말한 수치, 대상(노선·정류장·장소)을 원문에 쓰인 그대로 뽑는다.
- **계획**: 코드가 지칭마다 교통 자료의 후보를 붙이고 이동마다 가능한 조회를 만든다. 판정 모델이 실행할 조회를 고르고,
  언어 모델이 행정 검토용 요약(L1)과 조회마다 질문을 쓴다.
- **조회 실행**: 코드가 고른 조회를 조건 그대로 실행하고 근거로 남긴다.
- **답과 화면**: 언어 모델이 질문마다 답을 쓰고, 코드가 만든 블록 후보 중 페이지에 둘 것을 고른다.

민원 읽기는 추상에서 구체로 진행한다. 문제 유형을 먼저 정하고, 이동과 L1은 선택한 유형과 원문 근거를 입력으로 구성한다.
원문에 없는 요구·조건·시간대·방향은 더하지 않는다. 교통 자료로 볼 수 없는 민원은 조회 없이 L1만 남고, 이것은 정상 결과다.
조회를 하나 더 하는 것보다 틀린 조회를 막는 것을 우선한다.

## 구현

| 위치 | 언어 | 역할 |
|---|---|---|
| `backend/` | Go | 분석 단계(`dllio` 명령), 모델 호출, 교통 조회·계산 |
| `backend/db/` | PostgreSQL | 교통 자료 저장(`transit` 스키마) |
| `preprocess/` | Python | 교통 자료 전처리와 적재 |
| `viewer/` | Rust | 민원 검토 데스크톱 뷰어 |
| `raon/` | Python, shell | Raon 생성 서버 실행 |
| `prompts/` | | 모델 지시와 L2 catalog |
| `data/` | | 공통 시간·공휴일 사전 |
| 지역 디렉터리 | | 민원 원문, 지역 설정·사전, 교통 원천 자료와 전처리 결과. `DLLIO_REGION`으로 지정하며 기본값은 `examples/solmoe` |

판정은 local 판정 worker가 d3-ultra-INT4의 판정 readout으로 실행한다. 추출·계획·답변 생성은 Raon 생성 서버(Raon-1-mini-preview)가 실행하고, 서버는 함께 들어온 여러 민원의 요청을 한 batch로 생성한다.
